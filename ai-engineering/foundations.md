# 한 번의 주문 문의가 끝나기까지

“내 주문은 언제 도착하나요?”라는 질문에서 다음 행동은 현재 가진 정보에 달려 있다. 주문 번호가 있으면 조회하고, 없으면 질문한다. 처리 순서를 코드가 고정하면 워크플로다. 관찰한 결과를 바탕으로 모델이 다음 도구와 종료 시점을 선택하면 에이전트 루프가 된다. 두 경우 모두 권한 확인과 호출 횟수 제한은 실행 코드가 맡는다. [설계 원문](https://www.anthropic.com/research/building-effective-agents)

## 루프의 한 바퀴

1. 목표, 확인된 주문 번호, 최근 조회 결과를 모델에 전달한다.
2. 모델이 조회를 요청하면 코드가 허용된 도구인지, 입력이 유효한지, 현재 사용자가 이 주문을 볼 수 있는지 검사한다.
3. 조회 결과에 상태와 조회 시각을 붙여 모델에 돌려준다. 배송 예정일이 확인되면 근거와 함께 답한다.
4. 주문 번호가 필요하면 사용자 입력을 기다린다. 호출 예산을 모두 썼다면 확인된 사실과 남은 질문을 반환한다.

빈 조회 결과를 매번 같은 입력으로 재조회하면 비용만 늘어난다. ‘번호 없음’, ‘해당 주문 없음’, ‘일시 장애’를 구분하면 각각 질문, 종료, 제한된 재시도로 연결할 수 있다.

## 다음 판단에 필요한 컨텍스트

대화 전체를 매번 복사하면 지난 주문의 배송일이 이번 주문의 근거처럼 섞일 수 있다. 활성 주문 번호, 사용자 요구, 확인된 사실, 미확인 항목을 따로 보관한다. 긴 정책은 문서 ID와 판본을 남겨 두고 필요한 조항만 가져온다. 요약 과정에서 예외 조건이 사라질 수 있으므로 결론을 내리기 전에 원문 조항을 다시 조회한다. [컨텍스트 설계 원문](https://www.anthropic.com/research/effective-context-engineering-for-ai-agents)

## 도구 계약 예시

`lookup_order(order_id)`는 읽기 전용으로 설계한다. 호출자 신원은 인증된 세션에서 얻는다. 반환값에는 주문 상태와 조회 시각을 넣고, 배송일을 모르면 빈 값으로 둔다. 조회와 교환 신청은 별도 도구로 둔다. 그러면 조회 권한만 가진 세션에 신청 기능을 노출할 필요가 없다. 신청 결과를 받지 못한 경우는 [복구 노트](reliability.md)에서 다룬다.
