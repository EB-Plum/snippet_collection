# 다섯 가지 워크플로 선택하기

모델 호출을 추가하기 전에 단일 호출이나 규칙 하나로 같은 문제를 풀어 본다. 아래 흐름은 같은 주문 상담 업무에 서로 다른 제약을 준 예시다.

## 연쇄 실행

단계별 입력 형식이 정해져 있을 때 적용한다.

`문의 → 주문 번호 추출 → 형식 검사 → 답변 초안`

**실패 사례.** 주문 번호를 잘못 읽으면 다음 단계가 엉뚱한 주문을 설명한다. 형식 검사 뒤 실제 주문의 존재와 접근 권한도 확인한다.

**설계 질문.** 추출 단계에서 번호가 비어 있으면 어느 단계로 보내야 할까? 조회 전에 멈추고 사용자에게 주문 번호를 요청한다.

## 라우팅

서로 다른 처리 절차 중 하나를 골라야 할 때 적용한다.

`문의 → 유형 분류 → 배송 조회 또는 교환 안내`

**실패 사례.** 배송과 교환을 함께 묻는 요청은 하나의 분류값으로 뜻이 잘린다. 복합·미분류 경로를 두고 실제 문의로 분류 오류를 센다.

**설계 질문.** 분류기가 배송을 골랐지만 주문 번호가 없다면? 선택된 경로에서도 필수 입력을 검사한다. 누락된 번호를 추측하면 오분류가 잘못된 조회로 이어진다.

## 병렬 실행

필요한 하위 작업을 미리 알며 서로의 결과에 의존하지 않을 때 적용한다.

`주문 확인 → [재고 조회 ∥ 교환 정책 조회] → 결과 결합`

**실패 사례.** 재고 조회만 성공했는데 교환 가능으로 답할 수 있다. 두 결과에 각각 성공 여부와 기준 시각을 붙이고 필수 결과가 빠지면 보류한다.

**설계 질문.** 두 조회 중 정책 조회가 먼저 끝나면 답해도 될까? 교환 가능 여부에는 두 결과가 필요하다. 먼저 끝난 조회만으로 결론을 내리면 안 된다.

## 조정자와 작업자

문서를 열어 본 뒤에야 조사 범위가 드러날 때 적용한다.

`조정자 → 발견한 쟁점별 조사 → 근거와 결론 통합`

**실패 사례.** 두 작업자가 같은 조항을 반복 조사하거나 서로 다른 판본을 인용한다. 쟁점·판본·완료 조건을 배정하고 합칠 때 출처를 대조한다.

**설계 질문.** 항상 같은 두 문서만 조회한다면 어떤 구조가 간단할까? 고정 병렬 조회로 충분하다. 작업 목록 자체를 결정하는 호출을 줄일 수 있다.

## 평가와 개선

초안의 결함을 특정할 기준과 수정 기회가 있을 때 적용한다.

`초안 → 기준별 평가 → 통과 시 종료 · 미달 시 수정 후 재평가`

**실패 사례.** 평가자가 문체만 칭찬하면 잘못된 배송일이 살아남는다. 날짜를 조회값과 대조하고 수정 한도에 이르면 미해결 항목을 넘긴다.

**설계 질문.** 같은 오류가 반복되는데 계속 고치게 할까? 반복 한도와 개선 여부를 확인한다. 근거가 부족하면 추가 조회나 사람의 검토로 넘긴다.

패턴 분류의 출처는 [Anthropic의 설계 글](https://www.anthropic.com/research/building-effective-agents)이다. 각 문의 사례는 이 분류를 적용한 연습 문제다.
