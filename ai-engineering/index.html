에이전트 설계 연습장

“주문이 언제 도착하나요?”라는 문의 하나로 실행 순서, 도구 선택, 실패 복구를 연습한다.

다음 행동은 누가 고를까?

주문 번호 확인과 배송 조회의 순서를 미리 정할 수 있다면 코드로 그 순서를 표현한다. 조사 도중에야 다음 질문이 드러난다면 에이전트가 관찰 결과를 받아 다음 행동을 고르게 한다. 이때도 조회 권한과 종료 한도는 코드가 검사한다.

조건에 맞는 흐름 펼치기

연쇄 실행단계별 입력 형식이 정해져 있을 때

문의 → 주문 번호 추출 → 형식 검사 → 답변 초안

주문 번호를 잘못 읽으면 다음 단계가 엉뚱한 주문을 설명한다. 형식 검사 뒤 실제 주문의 존재와 접근 권한도 확인한다.

추출 단계에서 번호가 비어 있으면 어느 단계로 보내야 할까?

조회 전에 멈추고 사용자에게 주문 번호를 요청한다.

라우팅서로 다른 처리 절차 중 하나를 골라야 할 때

문의 → 유형 분류 → 배송 조회 또는 교환 안내

배송과 교환을 함께 묻는 요청은 하나의 분류값으로 뜻이 잘린다. 복합·미분류 경로를 두고 실제 문의로 분류 오류를 센다.

분류기가 배송을 골랐지만 주문 번호가 없다면?

선택된 경로에서도 필수 입력을 검사한다. 누락된 번호를 추측하면 오분류가 잘못된 조회로 이어진다.

병렬 실행필요한 하위 작업을 미리 알며 서로의 결과에 의존하지 않을 때

주문 확인 → [재고 조회 ∥ 교환 정책 조회] → 결과 결합

재고 조회만 성공했는데 교환 가능으로 답할 수 있다. 두 결과에 각각 성공 여부와 기준 시각을 붙이고 필수 결과가 빠지면 보류한다.

두 조회 중 정책 조회가 먼저 끝나면 답해도 될까?

교환 가능 여부에는 두 결과가 필요하다. 먼저 끝난 조회만으로 결론을 내리면 안 된다.

조정자와 작업자문서를 열어 본 뒤에야 조사 범위가 드러날 때

조정자 → 발견한 쟁점별 조사 → 근거와 결론 통합

두 작업자가 같은 조항을 반복 조사하거나 서로 다른 판본을 인용한다. 쟁점·판본·완료 조건을 배정하고 합칠 때 출처를 대조한다.

항상 같은 두 문서만 조회한다면 어떤 구조가 간단할까?

고정 병렬 조회로 충분하다. 작업 목록 자체를 결정하는 호출을 줄일 수 있다.

평가와 개선초안의 결함을 특정할 기준과 수정 기회가 있을 때

초안 → 기준별 평가 → 통과 시 종료 · 미달 시 수정 후 재평가

평가자가 문체만 칭찬하면 잘못된 배송일이 살아남는다. 날짜를 조회값과 대조하고 수정 한도에 이르면 미해결 항목을 넘긴다.

같은 오류가 반복되는데 계속 고치게 할까?

반복 한도와 개선 여부를 확인한다. 근거가 부족하면 추가 조회나 사람의 검토로 넘긴다.

실습 · 응답을 잃어버린 교환 신청

서버가 신청을 저장했지만 첫 응답이 도착하지 않았다. 아래 두 번째 호출이 돌려줄 접수 번호와 최종 신청 건수를 예측해 보자.

apply_exchange("intent-1", "A17")
receipt = apply_exchange("intent-1", "A17")
예상 결과와 이유

접수 번호는 1이고 신청도 한 건이다. 서버가 같은 키와 주문에 저장해 둔 접수 번호를 반환한다. 같은 키로 다른 주문을 보내면 충돌로 처리한다.
