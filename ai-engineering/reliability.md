# 상태를 남기고 결과를 검증하기

## 응답이 끊긴 교환 신청

서버가 신청을 저장한 직후 연결이 끊기면 호출자는 성공 여부를 모른다. 이때 새 요청으로 재시도하면 신청이 두 건 생길 수 있다. 최초 요청 전에 작업 ID를 저장하고 같은 의도의 재시도에는 그 ID를 재사용한다. 서버는 호출자와 작업 ID에 대응하는 기존 결과를 반환한다. 같은 키로 입력이 달라지면 충돌로 처리한다. 중복 방지 기록과 실제 변경은 함께 확정해야 한다. [AWS의 재시도 설계](https://aws.amazon.com/builders-library/making-retries-safe-with-idempotent-APIs/)

| 저장할 상태 | 재개할 때의 판단 |
| --- | --- |
| 실행 ID, 단계, 주문 번호 | 어느 문의를 어디까지 처리했는가 |
| 신청 키, 정규화한 입력, 결과 ID | 같은 의도인가, 이미 처리됐는가 |
| 마지막 오류, 남은 횟수 | 다시 시도할 수 있는 일시 장애인가 |
| 원문 근거와 조회 시각 | 이전 결론이 여전히 유효한가 |

상대 시스템이 키 기반 중복 방지를 지원하지 않으면 먼저 처리 결과를 조회한다. 결과 확인까지 불가능하면 불확실한 상태를 기록하고 검토로 넘긴다.

## 평가표 만들기

“신청했습니다”라는 문장이 자연스러워도 실제 신청이 두 건이면 실패다. 실행 기록은 원인을 조사하는 데 쓰고, 성공 판정은 테스트 환경의 최종 상태에서 읽는다. 모델 출력이 달라질 수 있으므로 같은 사례를 여러 번 실행하고 성공 횟수와 총 시행 수를 함께 기록한다. [에이전트 평가 원문](https://www.anthropic.com/research/demystifying-evals-for-ai-agents)

| 입력 또는 장애 | 기대하는 관찰값 |
| --- | --- |
| 주문 번호 없는 배송 문의 | 추가 질문을 하고 조회 횟수는 0 |
| 정상 교환 신청 1회 | 해당 주문에 신청 1건 |
| 저장 직후 응답 유실, 같은 키로 재시도 | 결과 ID가 같고 신청 1건 |
| 같은 키로 다른 주문 신청 | 충돌로 종료하고 추가 신청 0건 |

[실험](experiments/retry.py)은 마지막 두 조건을 메모리에서 검사한다. 프로세스 재시작과 동시 요청을 다루려면 영속 저장소의 고유 제약과 트랜잭션을 별도로 검증해야 한다.
